# Build systems for diff-based test selection, 2026-10-11

Question (Chris, via the controller): which build system or graph-aware task
runner should run only the tests a change can affect, across his repos, with
`sudokumaker-custom-constraints` as the pilot?

Tags used below: **(P)** = read from the cited page this session. **(I)** = my
inference. Nothing was installed or run against any candidate; every fit
statement is from docs plus a read of the repos.

## Short answer

- The candidates split into two kinds. **Pants, Bazel, Buck2 and Please** are
  build systems with a file-level or target-level graph. **Nx, Turborepo and
  moon** are task runners whose graph is projects, with per-task input globs.
- Only **Pants** infers Python edges from import statements with no extra
  generator (P). Bazel needs BUILD files, hand-written or generated by Gazelle
  (P). The three task runners take declared globs; none of the pages opened
  shows them reading Python imports.
- All of Pants, Bazel, Nx, Turborepo and moon cache test results on local disk
  with no remote service (P for each). For Buck2 I did not find a page saying
  so.
- All of them can run "execute this script, exit code is the verdict" without
  converting the test (P for Pants, Bazel, Buck2, Nx, moon; I for Turborepo
  and Please).
- All of them can make a Markdown file an input of a test, and in every one it
  is declared by hand (P).
- Both names recalled from memory exist: **pytest-impacted** (PyPI 0.35.0,
  2026-10-01) and **snob** (Rust CLI 0.2.3, 2025-08-02). Both select Python
  tests from a static import graph and a git diff (P).
- **Earthly** is out: its README says it "is no longer actively maintained"
  (P).
- My ranking for the pilot, not settled: moon, then Nx, then Pants, then
  Turborepo, then Bazel, then Buck2. Reasons and what would change it are in
  § Ranking for the pilot.

## Per-repo fit

### Pilot: `sudokumaker-custom-constraints`

The pilot's tests are scripts. Each tool has to answer three things: run a
script as a test, know what the script reads, and not fight uv and npm.

- **moon** (I). A project per `examples/<name>` and `finders/<name>`, one
  task per runner (`node`, `uv run`), `inputs` naming `_shared` through a
  `project://` input. No test file changes. Python and uv sit at the
  experimental tier, but a task that only runs `uv run file` needs the system
  toolchain, which is tier 0. Precision is the project, not the file: a
  change to `examples/_shared` selects everything that declares it.
- **Nx** (I). Same shape with `project.json` per unit and `{workspaceRoot}`
  input globs. `--explain` prints why a task was selected (P). It adds an npm
  dependency and a daemon. Whether it can see `.mjs` import edges between
  directories that are not packages is unread.
- **Pants** (I). The only candidate that could give file-level Python edges
  without hand-declared deps. Costs specific to this repo: the 47 `*.test.py`
  and 42 `test_*.py` scripts are not pytest, so each needs a
  `test_shell_command` or conversion; `test_shell_command` runs in a sandbox
  with only declared files, and 72 test files read files and 28 start
  subprocesses; every directory put on `sys.path` would need to be a source
  root, and 10 module basenames repeat across directories, which I expect to
  make import resolution ambiguous (not confirmed on any page); the JS backend
  is experimental and runs tests through `package.json#scripts.test`, while
  the pilot's are bare `node file`; `uv.lock` is not a format the lockfile
  page names.
- **Turborepo** (I). Needs a `package.json` beside every unit and npm
  workspaces, in a repo whose Python is half the tests. It shares its local
  cache across git worktrees automatically (P), which matters for a
  worktree-per-ticket workflow, and the page warns that an output holding an
  absolute path can then point at another checkout (P).
- **Bazel** (I). The most exact model and the largest change: BUILD files
  for 259 Python files and the `.mjs` tree, `uv.lock` re-expressed as
  `requirements.txt`, `package-lock.json` converted to `pnpm-lock.yaml`.
- **Buck2** (I). Same BUILD cost as Bazel, no versioned releases, an
  open-source test runner the docs call "simplistic", and toolchains that
  "may not work as well" (P).

### agent-skills (this worktree)

- Resolved from the prior note: **Pants shell support is stable** and covers
  `source` inference ("Pants will infer dependencies by looking for imports
  like `source script.sh` and `. script.sh`"; "Normally, Pants will not
  understand dynamic sources, e.g. using variable expansion") (P). Its shell
  test runner is shUnit2, which this repo does not use, so the 57 `.test.sh`
  suites would be `test_shell_command` targets (I). **Pants Rust support is
  experimental** and the backend table links no docs page for it (P).
- Resolved: **Bazel caches test results natively and locally**; the default
  `--cache_test_results=auto` reruns a test only when Bazel "detects changes
  in the test or its dependencies", it is `external`, `--runs_per_test` is
  set, or it failed. "Test results are always saved in Bazel's output tree"
  (P).
- The cross-directory Markdown reads the prior note lists (its items 2 and 4)
  are declared inputs in every candidate (P, row 3). No candidate discovers
  them.
- The `$here/../<dir>/` shell reads are variable expansions, the case Pants
  says it does not infer without a `# shellcheck source=` hint or an explicit
  dependency (P).
- The single Rust crate is one unit in any of them (I). moon lists Rust at
  full support (P).

### `gridfind`, `mediawiki-analytics`, `second-brain-v2` (pytest, uv)

- These are the repos where the pytest-level tools apply as written:
  pytest-impacted or snob add a dev dependency and a flag, no build files (I).
- Pants fits pytest directly (P: pytest is its Python runner), with the uv
  lockfile question open.
- With a task runner, each repo is one project, so "affected" selects all
  tests or none (I). The gain there is the local cache only.

### `visual-teach`, `research-queue` (Vitest), `twitch-rules-scroller` (`node --test`)

- Vitest's own `--changed` covers the two Vitest repos with no new tool (P).
- `twitch-rules-scroller` is 101 test files flat in one directory. A
  project-level runner sees one project (I). File-level selection there needs
  either an import-graph tool for `.mjs` or per-file tasks with declared
  inputs. I found no git-diff flag in `node --test`.

## Ranking for the pilot (mine, not settled)

1. **moon**: runs the existing scripts unchanged, inputs include other
   projects' files and Markdown, local cache, one binary, no daemon found in
   the pages opened, current release four days old.
2. **Nx**: same model with task-level `affected` and `--explain`; costs an
   npm dependency and a daemon.
3. **Pants**: best Python precision on paper, worst friction with this
   repo's script tests, `sys.path` layout and `.mjs` half.
4. **Turborepo**: wants `package.json` per unit; non-JS is second-class by
   its own guide.
5. **Bazel**: exact, and a rewrite of how the repo declares everything.
6. **Buck2**: Bazel's cost without Bazel's releases or ecosystem.

What would change this: a spike showing Pants infers the pilot's `sys.path`
imports cleanly would move it to first, because moon and Nx select by project
and Pants selects by file. A spike showing moon's `--affected` does not follow
`project://` inputs or `dependsOn` to downstream projects would drop it; the
run-task page only says the task's own inputs are intersected with changed
files.
