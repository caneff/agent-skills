# Autonomous coding-agent workflows end to end: prior art (2026-10-04)

Question: how do practitioners and vendors who run coding agents at scale structure the whole loop (sizing, building, reviewing, deciding "done", orchestrating, tuning the process)? What does that imply for this repo's burn, where 77% of 301 tickets in 14 days were about the burn/review tooling itself, each worker runs three parallel Opus reviewers, a verification pass, up to two Codex adversarial passes and the full seam, and the always-on rules have grown one rule per failure?

Method: web search and page fetch (Exa, curl), 2026-10-04. I read every source cited below except where marked "abstract only" or "secondary". The repo's own numbers come from the brief and were not re-measured here. This doc does not repeat the review-bot-noise and ticket-inflation material in `2026-10-04-agent-ticket-inflation.md`; it cites that doc where the two overlap.

Evidence grades used below: **vendor-internal** (a vendor reporting on its own use, unaudited), **peer-reviewed / preprint** (marked; most preprints here are not yet reviewed), **practitioner** (one person's or one team's account), **abstract only** (I did not read past the abstract).

## Synopsis

### What the field converges on

1. **One review wave per change, not a sequence of rounds.** Every vendor review system I could open runs one pass made of parallel reviewers plus a filter, and posts once. Anthropic's Code Review dispatches "a team of agents" that look for bugs in parallel, verify each candidate to drop false positives, rank by severity, and post a single summary. Its open-source plugin is four parallel reviewers, then one validation subagent per finding. OpenAI's reviewer is one repo-aware pass whose comments lead to a code change 52.7% of the time. Iteration in these systems is driven by *tests and CI*, not by re-running review. The one exception is OpenAI's internal Harness team, which loops "until all agent reviewers are satisfied". But that team runs with "minimal blocking merge gates" and lets agents merge their own PRs.
2. **Reviewers are told to report less, not more.** Anthropic's own Claude Code guide says a reviewer "prompted to find gaps will usually report some, even when the work is sound", and that "chasing every finding leads to over-engineering". Its advice is to flag only gaps that affect correctness or the stated requirements. The plugin's reviewer prompt says "if you are not certain an issue is real, do not flag it".
3. **Extra rounds have measured diminishing or negative returns.** Repair loops driven by test feedback get most of their gain in the first two to four iterations. Review or refine loops without new ground truth do worse. In one controlled study, multi-turn review produced 62% more false positives and a lower F1 than a single pass. In another, security got worse with each "improvement" round. One team's 222-round ledger never converged, and 57% of its later findings were about the previous round's fix. A second reviewer of a *different kind* (another model family, different inputs) finds a partly different set of bugs. A second pass of the same reviewer mostly does not.
4. **Short always-on instructions, with enforcement moved into code.** Anthropic says to keep each CLAUDE.md under 200 lines, delete any line whose removal would not cause mistakes, and turn rules into hooks. OpenAI's agent-only repo keeps a roughly 100-line AGENTS.md as a "table of contents", and "when documentation falls short, we promote the rule into code". The only controlled studies find context files add 20% or more to cost with no significant gain in correctness. At 500 instructions, the best model in IFScale satisfied 68% of them.
5. **Multi-agent pays only on decomposable, breadth-first work.** Anthropic's multi-agent research system uses about 15 times the tokens of a chat and notes that "most coding tasks involve fewer truly parallelizable tasks than research". Google/MIT measured +81% from multi-agent setups on decomposable tasks, −39% to −70% on sequential ones, and small losses on SWE-bench Verified once a single agent is above about 45% success. Independent parallel workers (one ticket per agent, no talking) fit that shape. Layers of agents supervising agents do not.
6. **"Done" means evidence from the environment, and the human moves up a level.** Tests, builds, screenshots, a recorded run, an evaluator with hard thresholds. GitHub requires a human approver who is not the issue's author. Cognition and Anthropic leave approval to a human. Addy Osmani: "human in the loop becomes human on the loop".
7. **Harnesses get ablated, not only grown.** Anthropic: "every component in a harness encodes an assumption about what the model can't do on its own". Their method is to remove one component at a time, keep only what is still load-bearing, and re-check when a new model ships. Several practitioners who built large agent systems report removing most of the layers again (51 agents cut to 2 roles; a six-hop path cut to 1 agent) once their own telemetry showed the oversight was catching errors that were not happening.

### Where this setup diverges, ranked by likely payoff

Rank is my judgement. Each item says what the field does, what the repo does, the proposed change, and its cost. Items that touch a standing ruling or hard rule are marked **decision for Chris**. I have not applied any of them.

## Q1. How practitioners and vendors structure the loop

**Anthropic (Claude Code guidance and its own systems).**
- "Best practices for Claude Code", Anthropic, docs page, undated (fetched 2026-10-04; the old https://www.anthropic.com/engineering/claude-code-best-practices now serves the docs page; markdown source https://code.claude.com/docs/en/best-practices.md). Done means a check: "Give Claude a check it can run... Without a check it can run, 'looks done' is the only signal available". The gates it describes, in order: same-prompt check, `/goal` with a separate evaluator, a Stop hook ("Claude Code overrides the hook and ends the turn after 8 consecutive blocks"), and "a verification subagent... so the agent doing the work isn't the one grading it". Review is a single fresh-context subagent pass: "Before treating a task as done, have a subagent review the diff in a fresh context and report gaps". The key caution, quoted in full: "A reviewer prompted to find gaps will usually report some, even when the work is sound, because that is what it was asked to do. Chasing every finding leads to over-engineering: extra abstraction layers, defensive code, and tests for cases that can't happen. Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional." Sizing: "If you could describe the diff in one sentence, skip the plan." Correction loop: "After two failed corrections, `/clear` and write a better initial prompt."
- "Code Review for Claude Code", Anthropic (claude.com blog), 2026-03-09, https://claude.com/blog/code-review . Vendor-internal. Runs on "nearly every PR at Anthropic"; substantive-comment rate rose from 16% to 54% of PRs. Large PRs (over 1,000 lines) get findings 84% of the time, averaging 7.5 issues; PRs under 50 lines, 31%, averaging 0.5. "Less than 1% of findings are marked incorrect." Structure: parallel agents, then a verify step, then severity ranking, then one overview comment. "It won't approve PRs — that's still a human call."
- `plugins/code-review/commands/code-review.md`, anthropics/claude-code repo at 2923bc87, undated, https://github.com/anthropics/claude-code/blob/2923bc87/plugins/code-review/commands/code-review.md . The concrete recipe: a cheap gate agent skips drafts, trivial PRs and already-reviewed PRs. Then 4 parallel reviewers (2 Sonnet for CLAUDE.md compliance, 2 Opus for bugs), then one validation subagent per finding, then a filter. "We only want HIGH SIGNAL issues"; do not flag "Potential issues that depend on specific inputs or state" or "Subjective suggestions". There is no second round.
- "Harness design for long-running application development", Anthropic Engineering, 2026-03-24, https://www.anthropic.com/engineering/harness-design-long-running-apps . Planner, generator and evaluator agents. Full harness $200 and 6 hours versus $9 and 20 minutes solo on the same prompt. On Opus 4.6 the author removed the sprint decomposition and "moved the evaluator to a single pass at the end of the run rather than grading per sprint". The DAW run used three build/QA rounds, with QA costing $3-4 per round against $71 for the first build. The evaluator "is worth the cost when the task sits beyond what the current model does reliably solo." (The doc on ticket inflation already cites this page for loop bounds; here it matters for its review placement.)
- "How we built our multi-agent research system", Anthropic Engineering, 2025-06-13, https://www.anthropic.com/engineering/multi-agent-research-system . Effort-scaling rules in the prompt: simple tasks get 1 agent and 3-10 tool calls, comparisons 2-4 subagents, complex research 10 or more. Early versions spawned "50 subagents for simple queries". See Q4 for cost.

**OpenAI.**
- Ryan Lopopolo, "Harness engineering: leveraging Codex in an agent-first world", OpenAI, 2026-02-11, https://openai.com/index/harness-engineering/ (fetched in full). Vendor-internal, one team. About 1M lines and about 1,500 merged PRs in five months; 3 engineers growing to 7; 3.5 PRs per engineer per day. Review loop: "instruct Codex to review its own changes locally, request additional specific agent reviews both locally and in the cloud, respond to any human or agent given feedback, and iterate in a loop until all agent reviewers are satisfied". "Humans may review pull requests, but aren't required to." Merge philosophy: "minimal blocking merge gates. Pull requests are short-lived. Test flakes are often addressed with follow-up runs rather than blocking progress... corrections are cheap, and waiting is expensive. This would be irresponsible in a low-throughput environment." Agents "often squash and merge their own pull requests". Quality is enforced in code: custom linters whose error messages carry remediation, structural tests, and "golden principles" applied by recurring background cleanup tasks whose PRs "can be reviewed in under a minute and automerged". The team used to spend every Friday (20% of the week) cleaning up "AI slop" by hand.
- "A Practical Approach to Verifying Code at Scale", OpenAI Alignment blog, 2025-12-01, https://alignment.openai.com/scaling-code-verification/ . Vendor-internal. Every internal PR is reviewed automatically; the reviewer has repo access and can execute code, which improved both precision and recall. Codex review comments on 36% of fully Codex-generated PRs; 46% of those comments lead to a change (53% on human PRs). Overall, authors change code for 52.7% of comments. The design goal is "high precision" and a "low safety tax".
- "Introducing upgrades to Codex", OpenAI, 2025-09-15, https://openai.com/index/introducing-upgrades-to-codex/ : Codex "reviews the vast majority of our PRs". The 13.7% vs 4.4% incorrect-comment figures (GPT-5 vs GPT-5-Codex) appear in secondary coverage (CIOL, 2025-09-16, https://www.ciol.com/news/openai-unveils-gpt-5-codex-with-github-reviews-and-ide-tools-10468777); I did not find them in the text of the OpenAI page itself, so treat them as unconfirmed.

**Steve Yegge (Gas Town).**
- Steve Yegge, "Welcome to Gas Town", 2026-01-01, https://yegge.ai/essays/welcome-to-gas-town/ (also on Medium). ## Q2. Review-round design

**Single pass vs iterative, measured.**
- Tae-Eun Song, "More Rounds, More Noise: Why Multi-Turn Review Fails to Improve Cross-Context Verification", arXiv 2603.16244, 2026-03-17, https://www.arxiv.org/pdf/2603.16244 . Single-author preprint; 30 artifacts with 150 planted errors. A single fresh-context review scored F1 0.376 and beat every multi-turn variant. Multi-turn raised recall by 0.08 but produced 62% more false positives (8.5 vs 5.2), so precision fell from 0.30 to 0.20. Independent re-review without prior context did worst (F1 0.263). The named mechanisms: "false positive pressure", where later rounds fabricate findings once the real ones are gone, and "review target drift".
- Shukla, Joshi, Syed, "Security Degradation in Iterative AI Code Generation", IEEE ISTAS 2025, arXiv 2506.11022, https://arxiv.org/html/2506.11022v1 . 400 samples × 10 "improve this" iterations: 37.6% more critical vulnerabilities after five iterations. Mean vulnerabilities per sample were 2.1 in early iterations and 6.2 in iterations 8-10. Recommends at most 3 consecutive LLM-only iterations. No test oracle was in the loop.
- arXiv 2603.08520 (authors not shown on the page I read), https://arxiv.org/pdf/2603.08520 : 43.7% of GPT-4o refinement chains had more vulnerabilities than baseline after 10 rounds. A SAST gate *raised* latent degradation from 12.5% to 20.8%, a "pseudo-safety effect" in which passing the gate licensed larger refactors. The relevance here: a gate a model can pass changes how it behaves.
- "Is Three the Magic Number? An Empirical Evaluation of LLM-Based Repair Loops", arXiv 2607.05197, 2026-07-06, https://arxiv.org/html/2607.05197 (abstract only): "the first three to four repair iterations account for most achievable gains". Repair behaviour depends more on workflow and feedback design than on the model.
- "How Many Tries Does It Take? Iterative Self-Repair in LLM...", arXiv 2604.10508, https://arxiv.org/html/2604.10508v1 (abstract only): with execution-error feedback, "Most gains concentrate in the first two rounds"; logic errors are repaired at about 45%.
- "Another Turn, Better Output?", arXiv 2509.06770, https://arxiv.org/html/2509.06770v2 (abstract only): for code, "code tends to grow in size with little semantic change"; after the first few turns, vague feedback "often plateaus or reverses correctness".

**Practitioner ledgers that look like this repo's.**
- "Why Two Independent Code Reviews Find Different Bugs" (dimantika.com, unsigned engineering post), 2026-09-14, https://dimantika.com/blog/two-reviewers-find-different-bugs . Single team, self-reported. An internal architect reviewer plus Codex, over 24 ledgers, 222 rounds and 21h21m of external review time. Per-round finding counts "wander instead of falling" (`7 4 2 4 1 5 5 4 3 2 2 2 2 2`). Of 167 blocking findings: 61% were "this test could be stricter", 38% repeated an earlier finding, and 57% were about something a previous round's fix introduced. 8% of rounds came back APPROVED. Their rule: a finding blocks only if it "names an executed mutant in a production file in the diff"; everything else becomes a task. They cap review at three rounds. They also argue *for* two reviewers with different inputs (the two agreed on 1 of 6 blocking findings across four stories). The rules went in on 25 August, so no after-data exists.
- "How Many AI Code Reviews Is Enough?" (EdgeLog), 2026-08-22, https://edgelog.dev/blog/how-many-ai-code-reviews/ . Single author, about 400 LLM calls, one firmware module. Ten independent reviews of unchanged code: one review found 44% of distinct defects, three found 71%, five 83%, eight 94%. 4 of the 14 groups were false, and the false ones were reported *more* often (6.8 of 10 runs) than the real ones (3.4 of 10). Giving the reviewer repo access removed those false positives. Alternating review and fix "produced no compliance gain while the code grew +24% to +152%". Prescription: "Review many times. Fix once." The author marks three of the six conclusions as replicated.

**Reviewer count and diversity.**
- Song, "When Does a Second Model Help? Cross-Model Review in LLM Verification", arXiv 2610.01471, https://arxiv.org/html/2610.01471 (abstract and summary only). Same planted-error setup: same-model and cross-model reviewers find partly different errors (Jaccard 41.2%). With two review calls, one same-model plus one cross-model call matched more errors than two same-model calls (56.7% vs 42.7%, p=.006).
- Tony Stone, "A Single LLM Is an Incomplete Code Reviewer", 2026-07-13, https://exa.ai/library/publication/fssn0m111t5 (abstract only): 294 confirmed issues; no model above about 61% recall on code; 56.8% of defects found by exactly one model; median cross-family Jaccard about 0.29.
- Hailu Xu, "Cross-Model LLM Code Review: Should you use Claude to review Codex or vice versa?", 2026-07-22, https://www.alphaxiv.org/abs/2607.21656 (abstract only): Claude reviewing Codex drafts raised pass rates from 71.6% to 89.7%. Codex reviewing Claude drafts *lowered* them from 91.4% to 82.8%, and Claude self-review left 91.4% unchanged. A reviewer can make a strong draft worse.
- Anthropic's plugin uses 4 parallel reviewers split by concern, then per-finding validation (Q1). Anthropic's Code Review uses an unspecified "fleet" plus a verify step.

**Writer/reviewer separation.** Anthropic recommends a fresh-context reviewer because "Claude won't be biased toward code it just wrote" (best practices, Writer/Reviewer pattern). The harness post: "tuning a standalone evaluator to be skeptical turns out to be far more tractable than making a generator critical of its own work". Beck's auditor genie (Q1) is the practitioner version. Osmani warns that same-family loops share blind spots.

**Tests as review.** Huntley's "backpressure", Reed's pre-commit hooks, Factory's "evidence required for every PR", Devin's test mode, and OpenAI's custom lints with remediation text all put the stopping signal in an executable check. The best-practices guide's Stop hook is the deterministic form of this. The weak point, per Beck and the defect classes in this repo's AGENTS.md: agents game tests (delete assertions), so tests need a check that they witness their claim. Mutation testing is the mechanism one team chose.

**Implication for this repo (inference).** The repo's own data has the same shape as the published evidence. The first wave finds almost everything; later sequential passes find little (Codex pass 2: 3 in 70; pass 3: 0 in 8); verification adds about 7.5% (37 in 492). A different reviewer adds more than a repeated one. So put the cross-family reviewer (Codex) into the first parallel wave, fix once, and let the seam be the convergence check.

## Q3. Process and rule accretion

**Size guidance from vendors.**
- "How Claude remembers your project", Claude Code docs, undated, https://code.claude.com/docs/en/memory : "Size: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." "Add to it when: Claude makes the same mistake a second time". Imports "still load and enter the context window at launch". Auto memory loads "first 200 lines or 25KB". "To block an action regardless of what Claude decides, use a PreToolUse hook instead."
- Best practices (Q1 citation): "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" "If Claude already does something correctly without the instruction, delete it or convert it to a hook." "If you emphasize many lines, none of them stands out."
- "Effective context engineering for AI agents", Anthropic Engineering, 2025-09-29, https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents : "the smallest possible set of high-signal tokens"; teams "stuff a laundry list of edge cases into a prompt... We do not recommend this."
- OpenAI Harness post (Q1): the "one big AGENTS.md" approach "failed in predictable ways". "Too much guidance becomes non-guidance... It rots instantly... It's hard to verify." They use about 100 lines as a map, with CI linters checking that the docs are fresh and cross-linked, plus a "doc-gardening" agent.
- Hari Srikanth, "Custom Code Review rules for Codex", OpenAI Developers, 2026-07-20, https://developers.openai.com/blog/custom-code-review-rules-for-codex : "broad instructions could easily create noise"; "narrow or remove guidance that repeatedly produces noise"; start with "two or three rules".
- Factory, "AGENTS.md" docs, undated, https://docs.factory.ai/harness/agents-md : "Do not use AGENTS.md as a dumping ground"; Factory, "How to write an AGENTS.md file", 2026-09-24, https://factory.com/articles/agents-md-guide : "Avoid responding to every failure with another page of general warnings."
- Cursor, "Rules" docs, undated, https://cursor.com/docs/context/rules : "Keep rules under 500 lines"; "Copying entire style guides: Use a linter instead."

**Measured effect of instruction volume.**
- Jaroslawicz, Whiting, Shah, Maamari, "How Many Instructions Can LLMs Follow at Once?" (IFScale), arXiv 2507.11538, 2025-07, https://arxiv.org/abs/2507.11538 . The best models reached 68% at 500 instructions. Reasoning models hold near-perfect to about 150-250 instructions, then decline. Bias toward earlier instructions peaks around 150-200. Errors shift from modification to omission under load. Claude Opus 4 scored 44.6% at 500. The task is keyword inclusion, so it measures compliance load, not judgement.
- Gloaguen, Mündler, Müller, Raychev, Vechev (ETH Zurich), "Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?", arXiv 2602.11988, 2026-02, https://arxiv.org/abs/2602.11988 . LLM-generated context files lowered success slightly (−0.5% and −2%, not significant) and raised cost 20-23%. Developer-written files gave +2.4% (p=0.21) at up to 19% more cost. "Instructions in context files are well followed", which is why cost rises: more tests, more file reads, more reasoning tokens. Conclusion: "unnecessary requirements from context files make tasks harder".
- "Do Context Files Help Coding Agents? A Two-Agent Ablation Study on Real Repositories", arXiv 2607.27250, https://arxiv.org/abs/2607.27250 : 288 runs across Claude Code and Codex. No measurable effect on correctness (bounded to 10-15 pp or less). A specific operational warning ("full suite takes >20 min") cut blind full-suite runs from 3.67 to 1.67 per task. Specific, operational lines earn their place; general ones do not.

**Rules per incident, and pruning.**
- Scott Beardsley, "I built 51 agents. Then I started removing some.", 2026-02-23, https://scott.beards.ly/blog/built-51-agents . Practitioner. "I let the agent fail. If it makes an architectural mistake once, I correct it. If it makes the same mistake again, that's evidence that the system needs a guardrail. Maybe that becomes a rule. Maybe it becomes a hook. Maybe a test should catch it." "I don't want the harness filled with instructions for hypothetical problems."
- OpenAI Harness: "When documentation falls short, we promote the rule into code."
- Zhang et al., "Agentic Context Engineering" (ACE), ICLR 2026, arXiv 2510.04618, https://arxiv.org/html/2510.04618 . The counter-case: *accumulating* playbooks beat terse rewritten ones (+10.6% on agent tasks), because monolithic LLM rewrites cause "context collapse". ACE stores each rule as an item with **helpful/harmful counters**, merges deltas deterministically, and dedupes by embedding. The lesson for a weekly retro is not "never add". It is that each rule carries a usage signal and gets pruned on that signal, and that the model does not rewrite the whole file.

**This repo against the guidance (inference).** About 670 always-on lines, against a vendor target of under 200 per file. The weekly retro adds a rule on the first occurrence; vendors say add on the second. Many rules here are procedural checks that a hook or test could carry. Nothing records whether a rule ever fired. The ETH result predicts the cost shows up as more steps and tokens rather than as failures, which fits a ledger of about 1.6M tokens per review (850M over about 520).

## Q4. Orchestration overhead

**Measured costs and where multi-agent pays.**
- Anthropic, multi-agent research system (Q1): "agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats". Token usage explains 80% of BrowseComp variance. "Most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time."
- Kim et al. (Google Research, MIT et al.), "Towards a Science of Scaling Agent Systems", arXiv 2512.08296; Google Research blog 2026-01-28, https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/ ; published as "Capable language models can outgrow the benefits of collaboration", Nature Machine Intelligence, 2026-07-24, https://www.nature.com/articles/s42256-026-01268-y . Peer-reviewed. Centralized multi-agent gave +80.8% on decomposable finance tasks; every multi-agent variant lost 39-70% on sequential planning. Above about 45% single-agent success, adding agents gives zero or negative gains. On SWE-bench Verified all multi-agent variants were slightly worse (−1.3% to −12.8%). Overhead was 1.6-6.2× reasoning turns. Independent agents amplify errors 17.2× and centralized ones 4.4×, which is evidence for a central validation step at the hand-off. Practical advice: "starting with a strong single-agent baseline, measuring coordination costs".
- Claude Code docs, "Agent teams", undated, https://code.claude.com/docs/en/agent-teams : "Agent teams add coordination overhead and use significantly more tokens than a single session... For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective." "Start with 3-5 teammates."
- Walden Yan, "Don't Build Multi-Agents", Cognition, 2025-06-12, https://cognition.ai/blog/dont-build-multi-agents : "Share context, and share full agent traces"; "Actions carry implicit decisions, and conflicting decisions carry bad results". "The simplest way to follow the principles is to just use a single-threaded linear agent." (Cognition later shipped "Devin can now Manage Devins", undated, https://cognition.com/blog/devin-can-now-manage-devins , for decomposable batch work such as per-page QA and per-package audits. That is the decomposable case the Google study favours.)

**People who simplified back down.**
- Beardsley (Q3): 50+ specialised agents cut to two roles (plan, implement), with hooks for mechanical steps. "The infrastructure itself became something the agent had to understand."
- Rajeev G., "My AI Agents Spent More on Oversight Than on Work", undated (canonical note dated 2026-08-29), https://rajeevg.com/blog/one-agent-two-models . Practitioner. Beads tracker, a verification pass, a worker-reservation preflight, a session manager and a frontier-model gate added up to six hops. Langfuse traces showed "Most of the oversight machinery was catching errors that weren't happening". New rule: "one agent per task, and you have to say why before you escalate". The tools stayed installed but no longer sit in the default path.
- Xingfan Xia, "I Rewrote My AI Coding Harness Four Times in Two Months", 2026-04-23, https://blog.ax0x.ai/harness-iteration : a heavy multi-agent phase framework (GSD) caught real bugs on large work but was resented "every time I wanted to ship a three-file feature". Heavy process paid on large work and cost on small work, so match the process to the size of the work.
- Jonathan Nen, "No agents, no plan, ship it", 2026-03-01, https://jonathannen.com/no-agents-no-plan/ : moved effort from plans and swarms into making the codebase let single prompts succeed; "Managing WIP is the key".
- Amp (Q1): specialised subagents removed for lack of use, then generic ones added back when the model changed. What a harness needs depends on the model.
- Anthropic harness post (Q1): removed the sprint construct and context resets as models improved. "Strip away pieces that are no longer load-bearing."

**Where this repo sits (inference).** Independent worker-per-ticket parallelism is the decomposable shape that pays. The controller's relay and monitoring role is the coordination tax; Gas Town needed a Witness agent for the same job. The review stage is itself a small multi-agent system (3 axes + verification + Codex). Its overhead is visible in the ledger (about 93 hours over about 520 reviews).

## Q5. Self-improvement loops and their bounds

The ticket-inflation doc already covers self-graded loops (Park and Choi's pilot, where an agent claimed improvement on every cycle while 56% did not improve), iteration caps, and the fragility of self-improving agents. New material:

- **Ablate one component at a time; re-test on each model release.** Anthropic harness post (Q1): after a radical cut failed, "I moved to a more methodical approach, removing one component at a time and reviewing what impact it had". Every component "encodes an assumption about what the model can't do on its own... they can quickly go stale as models improve."
- **Move learned rules into executable checks.** OpenAI Harness: human taste becomes lints and structural tests; "When the agent struggles... identify what is missing... and feed it back into the repository". The bound is that a rule only counts once a machine enforces it. Factory's guide says the same: "Treat written guidance and enforced controls separately."
- **Add on the second occurrence, from observed failures only.** Claude Code memory docs and Beardsley (Q3).
- **Per-rule usage signal and dedupe.** ACE (Q3): helpful/harmful counters per item, deterministic merges, embedding dedupe. Anthropic: "test changes by observing whether Claude's behavior actually shifts".
- **Measure from outside the loop.** Rajeev G. (Q4) used trace telemetry to discover that oversight layers were idle; the Google study recommends "measuring coordination costs" before keeping a layer. Cognition's Session Insights analyses finished sessions and proposes prompt changes (https://cognition.com/blog/how-cognition-uses-devin-to-build-devin); I found no data on how far those changes improve later sessions.
- **Agents can tune their own tools, with a measured target.** Anthropic's tool-testing agent rewrote tool descriptions and cut task time 40% for later agents (multi-agent research post). The bound there was an objective metric (completion time), not the agent's own judgement.
- **Accept loss as a design choice.** Yegge (Q1) runs the opposite policy: he tolerates lost and duplicated work for throughput and keeps the tracker small (ticket-inflation doc). Nothing in his posts measures the quality cost.

**Implication for this repo (inference).** The weekly retro is a self-improvement loop with no out-of-band check that a new rule changed anything. The cheapest bounds the sources support: (1) the ledger becomes the judge, and a rule or review component stays only if switching it off raises escapes; (2) a fixed line budget for always-on files; (3) promote to a hook or test, or drop.
